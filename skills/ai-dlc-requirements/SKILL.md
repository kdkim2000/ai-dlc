# AI-DLC 요구사항 정의서 작성기

사용자의 자연어 입력(사업 설명·기능 메모·회의록 등)을 분석해 AI-DLC 방법론의 표준 목차를 따르는 한국어 요구사항 정의서를 생성한다. 초안을 한 번에 만든 뒤, **누락된 핵심 항목만 묶어** 한 차례 추가 질문해 완성도를 높인다.

## 트리거

다음 표현이 나오면 자동 발동한다:
- `요구사항 정의서`, `요구사항 명세서`, `요구사항 문서화`
- `AI-DLC`, `AI DLC`, `AIDLC`
- `RFP`, `제안요청서`, `SI 요구사항`, `사업 요구사항`
- 사용자가 "이걸로 요구사항 문서 만들어줘" 류의 요청을 할 때

## 하이브리드 진행 절차

1. **입력 파싱**: 사용자가 제공한 모든 텍스트에서 다음을 추출
   - 사업명, 사업 목적/배경, 사업 기간, 사업 예산, 발주자/수행자
   - 기능 후보(동사+목적어 형태), 비기능 후보(응답시간·동시접속·인증 등 키워드)
   - 기술스택 키워드(FE/BE/DB/Infra/Cloud 카테고리)
   - 참고 문서/링크
2. **초안 생성**: `${CLAUDE_SKILL_DIR}/template.md`를 읽어 자리표시자(`{{...}}`)를 추출 결과로 치환. 분류가 애매하면 `${CLAUDE_SKILL_DIR}/references/id-codes.md`를 참조해 결정.
3. **핵심 누락 항목만 묶음 질문** (한 번만, 묶어서):
   - 사업명 / 사업기간 / 사업예산 중 비어 있는 것
   - 추진 배경이 한 문장도 없을 때
   - 핵심 기능이 3개 미만일 때 추가 기능
   - 기술스택 카테고리(FE/BE/DB/Infra) 중 비어 있는 카테고리
   - **3개 이하**로 추려서 한 번에 질문. 그 이상이면 인터뷰 모드로 전환(아래 엣지 케이스 참조).
4. **답변 반영 후 최종 출력**: 출력 정책에 따라 파일 저장 또는 대화창 출력.

## 요구사항 ID 채번 규칙

| 분류 | Prefix | 예시 |
|:---|:---|:---|
| 기능 | `FR` | FR-001 |
| 성능 | `PR` | PR-001 |
| 보안 | `SR` | SR-001 |
| 품질 | `QR` | QR-001 |
| 인터페이스 | `IR` | IR-001 |
| 데이터 | `DR` | DR-001 |
| 제약 | `CR` | CR-001 |

- 형식: `{PREFIX}-{NNN}` — 3자리 0 패딩, 분류별 001부터 순차.
- 한 문서 내에서 prefix별로 **독립 채번** (FR과 PR이 동시에 001을 가질 수 있음).
- 분류 판단이 애매할 때는 `references/id-codes.md`의 가이드를 따른다.

## 출력 정책

**기본: 파일 생성 모드**
- 저장 경로: 작업 디렉터리 기준 `요구사항정의서_{사업명}_{YYYYMMDD}.md`
- 사업명에서 OS 금지 문자(`\ / : * ? " < > |`)와 공백은 `_`로 치환.
- 생성 후 답변에 **절대 경로**와 한 줄 요약(섹션별로 채워진 항목 수, 예: `FR 5건 / PR 2건 / SR 1건...`)을 포함.
- 동일 파일이 이미 존재하면 덮어쓰기 전에 사용자에게 확인.

**대화창 출력 모드** (다음 키워드가 입력에 있으면 전환):
- `"보여만 줘"`, `"파일 만들지 마"`, `"여기에 출력"`, `"대화창에"`, `"표시만"`
- 파일을 만들지 않고 마크다운 본문 전체를 대화창에 출력.

## 작성 원칙

- **표는 GFM 표 문법** 사용, 헤더 구분자에 정렬 명시(`:---`, `:---:`, `---:`).
- 추측한 내용은 `<!-- TODO: 확인 필요 -->` 인라인 주석으로 표시해 사용자가 채울 수 있게 함.
- **요구사항 총괄표**는 모든 분류의 건수 합계를 보여주는 단일 표. 분류별 상세는 2장 각 절과 별지서식에 분리.
- **별지서식**:
  - 기능 요구사항 목록 = FR 항목 전체
  - 비기능 요구사항 목록 = PR + SR + QR + IR + DR + CR
- 문서 버전 이력의 초기 행: `v0.1 / {오늘 YYYY-MM-DD} / 초안 작성 / 초안 생성`
- 참고 문서가 입력에 없으면 섹션을 비우지 말고 `_(해당 없음)_` 한 줄로 채움.
- **오타 정정 정책**: 사용자 요청에 "품지 ㄹ요구사항" 같은 명백한 오타가 있어도 문서에는 **"품질 요구사항"** 으로 정확히 표기.

## 엣지 케이스

- **입력이 한두 줄로 너무 짧을 때** (예: "쇼핑몰 만들거임"): 묶음 질문이 4개 이상 필요해지므로 인터뷰 모드로 전환 — 사업개요부터 순서대로 한 섹션씩 짧게 물어보며 진행.
- **영어가 섞인 입력**: 문서는 한국어로 통일하되 고유명사(브랜드명·기술명)는 원문 유지.
- **사업명을 도저히 추출할 수 없을 때**: `{{사업명}}` 자리에 `_(미정)_`을 넣고 파일명은 `요구사항정의서_미정_YYYYMMDD.md`.
- **사용자가 일부 섹션 생략 요청** (예: "기술스택은 빼줘"): 해당 섹션을 비우지 말고 `_(이번 단계 범위 외)_` 한 줄로 처리. 목차 번호 유지.
- **반복 작성 요청**: 동일 파일명 존재 시 덮어쓰기 여부를 확인. 사용자가 "다시 써줘"라고 하면 기존 내용 무시.
